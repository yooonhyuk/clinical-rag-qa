# ADR 0002. embedding 모델: nomic-embed-text → bge-m3

- 상태: 채택 (2026-10-06)
- 관련: [이슈 001](../issues/001-korean-embedding-unk.md) (GitHub #1), commit `1c7cacc`, `c44e7d2`
- 관련 코드: `backend/app/config.py`(`KNOWN_EMBEDDING_MODELS`), `backend/app/services/embedding_schema.py`, Alembic `0004`, `scripts/diagnose_embedding.py`

## Context

MVP-1은 Ollama의 `nomic-embed-text`(768차원)로 chunk와 질문을 embedding했습니다. 질문의 대부분(toy 25문항 전부, public 99문항 중 66%)이 한국어이고, 문서는 한국어·영어가 섞여 있습니다. 첫 실제 평가(toy, 2026-10-06)에서 벡터 단독 검색의 hit@5가 63.2%, 오거절이 63.2%였습니다. 원인을 찾기 전까지는 "소형 생성 모델이 표를 놓친다"는 가설도 있었습니다.

## Options

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. nomic-embed-text 유지 + 하이브리드(pg_trgm) | 모델 274MB, 이미 동작 | 한국어 벡터가 무너진 상태를 가림, cosine 거절 임계값이 무의미 |
| B. bge-m3 (Ollama, 1024차원) | 다국어 XLM-RoBERTa 어휘(250k, 한글 음절 토큰 5,373개), Ollama에서 바로 실행 | 모델 1.2GB, 질문 embedding 지연 증가, 차원 변경 → 전체 재인덱싱 |
| C. 다른 다국어 모델(e5, gte 등) | - | Ollama 공식 배포·오프라인 번들 경로를 따로 만들어야 함. 측정하지 않음 |

## Decision

기본 embedding 모델을 **bge-m3**로 바꿉니다. 모델·차원·prefix는 설정(`OLLAMA_EMBEDDING_MODEL`, `EMBEDDING_DIM`)으로 바꿀 수 있고, 모든 chunk·문서·인덱싱 작업에 `embedding_model`을 기록합니다. 검색은 설정된 모델의 chunk만 읽습니다.

## Evidence (measured)

토크나이저 진단(`scripts/diagnose_embedding.py`, Ollama 0.24.0, 2026-10-06):

| | nomic-embed-text | bge-m3 |
|---|---|---|
| 어휘 크기 | 30,522 | 250,002 |
| 한글 음절이 들어간 토큰 | **0** | 5,373 |
| cos("업로드", "태그") | **1.0000** | 0.5830 |
| cos("헬프데스크 운영 시간은 언제인가요?", "이 CT에 폐결절이 있나요?") | **1.0000** | 0.4159 |
| cos("upload", "tag") (대조군) | 0.4708 | 0.5430 |

toy 25문항(답 19 / 거절 6), gemma4:e4b, top_k=5, `MIN_RELEVANCE_SCORE=0.45` ([이슈 001](../issues/001-korean-embedding-unk.md) "전후 지표"):

| 지표 | nomic · 벡터 | nomic · 하이브리드 | **bge-m3 · 벡터** | bge-m3 · 하이브리드 |
|---|---|---|---|---|
| hit@5 (파일) | 63.2% | 94.7% | **100%** | 100% |
| Section hit@5 | 31.6% | 68.4% | **100%** | 100% |
| False refusal | 63.2% | 21.1% | **0%** | 0% |
| Refusal correctness | 100% | 100% | **100%** | 100% |
| Retrieval p50 | 26 ms | 43 ms | 78~81 ms | 94~96 ms |

- bge-m3에서 답이 있는 질문의 최대 cosine은 0.555~0.753, 거절 대상은 0.428~0.651로 nomic(0.614~0.749 vs 0.730~0.807)보다 잘 갈라졌습니다. 그래서 NO_EVIDENCE(cosine 0.45) 단계가 처음으로 실제로 동작했습니다(q24).
- public 99문항(2026-10-07, bge-m3 · 벡터)에서는 hit@5 94.9%, 섹션 hit 86.1%였습니다. nomic으로는 public을 실행하지 않았습니다.

## Not measured

- nomic-embed-text의 public 코퍼스 성능(실행하지 않음).
- bge-m3 외 다국어 embedding 모델(e5, gte, Qwen3-Embedding 등).
- bge-m3의 sparse·multi-vector(ColBERT) 출력: Ollama는 dense 벡터만 제공합니다.
- 인덱싱 처리량의 정밀 비교(public 2,029 chunk 인덱싱이 약 2분이라는 관찰만 있음).

## Consequences

- 오프라인 번들에 embedding 모델 1.2GB가 들어갑니다(nomic 274MB).
- 모델이나 차원을 바꾸면 벡터를 모두 지우고 재인덱싱해야 합니다(`make reset-embeddings` → `make index`). 그동안 검색 결과가 비고 `/api/health`가 `degraded`를 보고합니다.
- 하이브리드는 이 결정 이후 이득이 없어 기본값에서 뺐습니다([ADR 0003](0003-retrieval-mode.md)).
- 교훈: embedding 모델을 고를 때 대상 언어 문자가 어휘에 있는지, 무관한 문장 쌍의 cosine이 1.0이 아닌지부터 확인합니다.

## 2026-10 재평가: EmbeddingGemma 2 (270m) vs bge-m3

> 상태: **bge-m3 유지 권고(불채택).** 기본값(`OLLAMA_EMBEDDING_MODEL=bge-m3`)은 바꾸지 않았고, 바꾸는 결정은 이 문서를 승인한 뒤에만 합니다. 위 결정은 뒤집지 않고 이 절을 덧붙입니다.

### 왜 다시 쟀나
호스트 Ollama를 0.24.0 → **0.40.2**로 올렸고, 후보 `embeddinggemma-2:270m`(텍스트 전용, 768차원, Matryoshka 512/256/128)·`:740m`이 이미 호스트에 있었습니다. 한국어 성능은 공개되지 않았고 bge-m3와 직접 비교한 수치도 없어서, **Ollama 0.40.2에서 bge-m3 기준선부터 다시** 쟀습니다(서로 다른 Ollama 버전의 결과는 비교하지 않음). 모든 실행은 같은 조건입니다: 일회용 pgvector 0.8.0 DB(모델마다 새로 만들어 toy 32 / public 2,029 / private 8,447 chunk 색인), `--vector-search exact`, gemma4:e4b(`think:false`), reranker 없음, top_k=5, chunk 1000/150. 접두어는 질의 `task: search result | query: `, 문서 `title: none | text: `(문서별 제목은 넣지 않음).

### 측정 전 확인한 것
- **bge-m3 기준선이 0.24.0과 같은가**: 표본 chunk 20개의 저장된 벡터(0.24.0)와 지금 다시 계산한 벡터의 cosine이 최소 0.99998 / 평균 0.999996. chunk 수(32 / 2,029 / 8,447)도 같습니다. 검색 지표(public hit@5 96.2%, 섹션 87.3%, private hit@5 75.0%, 섹션 45.3%)가 0.24.0과 같고, 생성에 의존하는 지표만 소폭 달랐습니다.
- **Ollama 0.40.2의 생성 동작 변화**: gemma4:e4b가 기본으로 thinking을 켜서(짧은 질문에 660토큰, 질문당 약 45초, 0.24.0 때 p50 4.4초) `OllamaClient`가 `think:false`를 보내도록 했습니다(0.24.0과 같은 비-thinking 동작). thinking이 켜진 첫 기준선 실행은 중단하고 버렸습니다. 또 0.40.2가 gemma4:e4b를 로컬에서 GGUF 호환 형식으로 변환했습니다(다운로드 아님). **생성 지표(Citation·Keyword·거절)는 0.24.0과 런타임·포맷이 달라 직접 비교하지 않습니다.**
- **`dimensions` 파라미터**: Ollama 0.40.2 `/api/embed`는 `dimensions`를 지원합니다. 270m·740m, 512/256/128, 입력 3개에서 서버 결과가 "앞 N차원 절단 + L2 정규화"와 최대 오차 6.6e-8로 같고 노름은 1입니다. 그래서 클라이언트 절단 대신 `EMBEDDING_TRUNCATE_DIM`을 `dimensions`로 보냅니다(1024는 400 오류 `dimensions 1024 exceeds embedding length 768`).
- **270m과 740m은 텍스트 벡터가 같습니다**: 6개 입력에서 두 모델의 768차원 벡터가 **비트 단위로 동일**(max|diff| = 0.0)합니다. `ollama show`의 capability는 740m이 embedding·vision·audio, 270m이 embedding이므로, 740m은 vision·audio 타워가 추가된 모델이고 텍스트 경로는 같은 것으로 보입니다(추정: 가중치를 직접 비교하지는 않았고, 확인한 것은 capability와 출력이 같다는 사실입니다). 그래서 740m은 별도 색인·평가를 하지 않았습니다(결과가 같을 수밖에 없음).

### 임계값 (측정 전에 정한 규칙, 보고서에 사전 등록)
- `scope_margin`: `scope_exemplars.yaml` 예시만으로 leave-one-out(k=3) Youden J 최대 지점(bge-m3 때와 같은 방법). 모델마다 다시 구했습니다: bge-m3 0.056, 270m 768d **0.0198**, 512d **0.0369**, 256d **0.0191**.
- `min_relevance_score`(cosine 게이트): 게이트를 끈 실행(`--min-relevance-score -1`)을 dev(toy 전부 + public 짝수 번째, 77문항)에서 재생해 `거절 정확도 − 오거절률`을 최대화(`eval/tune_cosine_gate.py`, held-out 절반은 읽지 않음). **결과는 모든 모델에서 "게이트 없음"과 같습니다**(bge-m3 −0.235, 270m −0.150 / −0.148 / −0.145: 최대값 구간의 중점이 음수라 어떤 질문도 걸러지지 않음). dev의 거절 대상 17문항은 범위 판별기·생성 모델이 이미 모두(bge-m3는 16개) 거절해서 게이트가 얻을 것이 없고, 오거절만 늘기 때문입니다. 사전 등록한 규칙을 바꾸지 않았고, 규칙을 바꾼 비교는 하지 않았습니다.
- 그래서 비교의 주 대상은 **(b) 같은 규칙의 bge-m3(게이트 없음)** 대 **(c) 270m**입니다. (a) 출하값 0.45 bge-m3는 참고로 함께 둡니다.

### 결과
생성 gemma4:e4b, 각 칸은 toy(25) / public 1·2회(99) / private(79). public 두 값은 1회 / 2회. 결과 폴더: `eval/results/2026-10-10_*`(label에 모델·차원).

| hit@5 toy / public / private | 100 / 96.2 / 75.0 | **100 / 96.2 / 75.0** | 89.5 / 92.4 / 68.8 | 89.5 / 91.1 / 75.0 | 84.2 / 92.4 / 70.3 |

| Keyword toy / public / private | 94.7 / 91.9 / 59.4 | 94.7 / 92.0 / 64.1 | 94.1 / 88.6 / 65.5 | 88.2 / 86.1·86.3 / 59.4 | 88.2 / 88.9 / 62.0 |

- **검색은 270m이 어느 코퍼스에서나 같거나 낮습니다.** public hit@5는 96.2% → 92.4%(79문항 중 3문항), 섹션 hit는 87.3% → 81.0%, toy hit@5는 100% → 89.5%(19문항 중 2문항), private 섹션 hit는 45.3% → 34.4%. 512d는 768d와 public hit@5·섹션 hit에서는 거의 같고(hit@5 91.1% / 92.4%, 섹션 hit 81.0% 동일), 섹션 hit는 256d가 모든 코퍼스에서 가장 낮고(public 79.7%, private 31.2%) toy hit@5도 256d가 가장 낮지만(84.2%), hit@5 차이는 코퍼스별로 다릅니다. public은 1문항 차(512d 72/79 = 91.1%, 256d·768d 73/79 = 92.4%), private은 4문항 차(768d 44/64 = 68.8%, 256d 45/64 = 70.3%, 512d 48/64 = 75.0%)입니다. private hit@5가 512d에서 75.0%로 bge-m3와 같은 것은 1회 실행이고, 섹션 hit는 34.4%로 낮아 한 칸으로 우위를 말할 수 없습니다.
- **B6 범위 판별기(예시 kNN)는 270m이 더 약합니다**: 오거절 2.8% → 5.6~8.3%, 정밀도 95.8% → 88.5~92.0%(held-out 61문항, 한 문항이 1.6%p).
- **Citation 정확도는 public에서 270m이 높게 나왔지만**(85~87% → 89~93%) 이는 생성 모델이 답하는 문항이 달라진 효과를 포함하고(오거절 5.1% → 7.6~11.4%), 검색 지표가 같이 올라가지 않았으므로 장점으로 읽지 않습니다.
- **장점은 크기·속도입니다**: 디스크 378MB(bge-m3 1.2GB, `ollama list`), 적재 메모리 346MB(673MB, `ollama ps`), 질문 embedding p50 13.3ms(16.9ms). 색인 시간은 768d·512d가 bge-m3와 비슷(288초 vs 267초)하고, 256d의 첫 색인은 443초였지만 절전 뒤 다시 만든 DB에서 재색인하니 private 288.5초, public 76.1초로 768d·512d(288초 / 76초)와 같았습니다. 443초는 첫 색인 때의 호스트 변동이었습니다.
- public 2회 실행에서 검색 지표(hit·섹션)는 모든 설정에서 같았고, 생성 지표는 Citation·Keyword가 최대 1.5%p, 거절 정확도는 한 문항(5%p)까지 흔들렸습니다.

### 결정 권고
**불채택, bge-m3 유지.** 같은 규칙·같은 색인의 비교에서 270m은 검색(hit@5, 섹션 hit)과 범위 판별기에서 열세이고, 이득은 모델 크기(디스크 약 1/3, 적재 메모리 `ollama ps` 약 1/2)와 질문 embedding p50 3.6ms 차이(16.9 → 13.3ms)뿐입니다. 한국어·영어 혼합 임상 문서에서 정확도가 이 프로젝트의 병목이므로 이득이 크기를 상쇄하지 못합니다. 디스크·메모리가 제약인 환경(폐쇄망 번들 용량 등)에서만 512d(저장 벡터 크기 1/2)를 후보로 다시 볼 수 있습니다.

### 측정 안 함
- 문서별 실제 제목을 넣은 문서 접두어(`title: <제목> | text:`): 코드가 chunk에 제목을 갖고 있지 않아 `title: none`만 측정했습니다. 모델 카드는 제목을 넣을 때 성능이 오른다고 하므로 270m에 유리한 조건을 쓰지 않은 결과입니다.
- 128차원, 740m(텍스트 벡터가 270m과 동일하다는 것만 확인), 740m의 멀티모달.
- Ollama가 제공하는 270m 빌드의 양자화(`ollama show`: nvfp4, mlx 러너)가 정확도에 준 영향. 원본 가중치와의 비교는 하지 않았습니다.
- 게이트(`min_relevance_score`)의 다른 목적함수. 위 사전 등록 규칙의 결과가 "게이트 없음"이라, 게이트를 켠 비교는 하지 않았습니다.
- private은 모델당 1회 실행입니다(hit·섹션은 두 번 같을 것으로 보이나 생성 지표 흔들림은 확인하지 않음).
