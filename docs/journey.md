# 개발 여정: 문제 → 시도 → 결과 → 교훈

MVP-1부터 B7(reranker)·생성 모델 비교까지, 실제로 부딪힌 문제를 시간 순서로 적었습니다. 수치는 모두 `eval/results/`와 `docs/issues/`에 남은 실행 결과에서 가져왔고, 측정하지 않은 것은 **(측정 안 함)** 으로 표시했습니다. 실행 환경은 따로 적지 않으면 Apple M5 / 32GB / macOS, 호스트 Ollama 0.24.0, 일회용 `pgvector/pgvector:0.8.0-pg16` DB입니다.

## 1. toy 평가와 한국어 `[UNK]` (2026-10-05 ~ 10-06)

- **문제**: 직접 만든 toy 코퍼스(가상 문서 6개, 25문항)로 첫 평가를 돌리자 벡터 단독 검색의 hit@5가 63.2%, 답이 있는 질문의 오거절이 63.2%였습니다. 답이 있는 질문과 거절 대상의 top-1 cosine(0.614~0.749 vs 0.730~0.807)이 겹쳐 어떤 임계값으로도 나눌 수 없었습니다.
- **시도**: 처음에는 "소형 생성 모델이 표를 놓친다"고 의심했습니다. 평가 러너가 문항별 `maxCosine`을 남기게 하고, `scripts/diagnose_embedding.py`로 토크나이저 어휘를 직접 셌습니다.
- **결과**: nomic-embed-text의 WordPiece 어휘(30,522개)에 한글 음절 토큰이 **0개**였습니다. 한국어 단어는 모두 `[UNK]`가 되어 cos("업로드", "태그") = 1.0000, 서로 무관한 두 한국어 질문의 cosine도 1.0000이었습니다([이슈 001](issues/001-korean-embedding-unk.md)).
- **교훈**: embedding 모델은 벤치마크보다 대상 언어 문자가 어휘에 있는지부터 봅니다. 점수 분포가 겹치면 모델 탓을 하기 전에 입력 표현을 확인합니다.

## 2. 하이브리드 검색으로 임시 대응 (2026-10-06)

- **문제**: 원인을 찾기 전, 한국어 질문을 당장 검색되게 해야 했습니다.
- **시도**: pgvector cosine 순위와 pg_trgm `word_similarity` 순위를 RRF(k=60)로 합쳤습니다(commit `4dfa5f7`).
- **결과**: toy에서 hit@5 63.2% → 94.7%, 오거절 63.2% → 21.1%. 하지만 무너진 벡터 채널이 RRF에서 같은 가중치를 가져 정답이 밀렸고(q05, q15), 거절 임계값에 쓰는 cosine은 여전히 의미가 없었습니다.
- **교훈**: 임시 대응은 증상을 가립니다. 지표가 올랐다고 원인이 해결된 것은 아닙니다.

## 3. bge-m3로 근본 해결 (2026-10-06)

- **문제**: 한국어를 표현할 수 있는 embedding 모델이 필요했습니다.
- **시도**: Ollama의 bge-m3(XLM-RoBERTa 어휘 250,002개, 한글 음절 토큰 5,373개, 1024차원)로 바꾸고, chunk마다 `embedding_model`을 기록해 다른 모델의 벡터를 섞지 않게 했습니다(Alembic `0004`).
- **결과**: toy 벡터 단독 hit@5 100%, 섹션 hit 100%, 오거절 0%. 답이 있는 질문의 cosine 0.555~0.753, 거절 대상 0.428~0.651로 갈라져 NO_EVIDENCE(0.45) 단계가 처음으로 실제로 동작했습니다. bge-m3에서는 하이브리드가 이득이 없어(Citation 한 문항 낮음, 검색 +15ms) 기본값에서 뺐습니다([ADR 0002](decisions/0002-embedding-model.md), [ADR 0003](decisions/0003-retrieval-mode.md)).
- **교훈**: 원인을 고친 뒤에는 임시 대응을 다시 측정해 빼야 합니다. 벡터에는 만든 모델을 함께 저장합니다.

## 4. DICOM PHI 노출과 표준 기반 재구성 (2026-10-06)

- **문제**: DICOM 분석기가 denylist(`PatientName` 등)에 없는 태그는 값을 그대로 응답·DB·LLM 프롬프트에 넣었습니다. `StudyDescription` 같은 자유 텍스트에 환자 정보가 들어갈 수 있습니다([이슈 002](issues/002-dicom-free-text-phi-to-llm.md)). 규칙도 손으로 쓴 YAML이었습니다.
- **시도**: 출력 경계를 **allowlist**(`dicom_safe.py`: 코드·숫자 값만, 나머지는 `exists/empty/absent`)로 바꾸고, 규칙을 DICOM 표준 원문(PS3.3 / PS3.15 / PS3.16 2026d DocBook XML)에서 생성하도록 재구성했습니다(Layer 1 적합성, Layer 2 Annex E 비식별화, #3).
- **결과**: 회귀 테스트가 응답 본문·DB 행·LLM 프롬프트·로그 모두에서 PHI 유사 문자열이 나가지 않음을 확인합니다. 대문자 이름이 CS 형식을 통과하는 경우(`BodyPartExamined = "HONG GILDONG"`)는 Defined Terms 대조로 막았습니다.
- **교훈**: 개인정보 경계는 denylist로 지킬 수 없습니다. "나가도 되는 것"을 적습니다.

## 5. 폐쇄망 egress 하드닝 (2026-10-06)

- **문제**: 오프라인 프로필에서 ui 컨테이너만 호스트 포트 공개를 위해 일반 bridge(`ui_edge`)에 붙어 있었고, 그래서 인터넷으로 나갈 수 있었습니다. 기존 `verify-offline.sh`는 api에서 HTTP 3곳만 확인해 이를 잡지 못했습니다([이슈 003](issues/003-offline-ui-egress.md)). compose는 0.0.0.0에 포트를 열고 호스트 Ollama 설정을 무시했습니다([이슈 004](issues/004-compose-host-ollama-and-port-binding.md)).
- **시도**: Docker 설정 5가지를 직접 시험했지만(masquerade 끄기, isolated gateway, gw-priority 등) 포트 공개와 egress 차단을 동시에 만족하지 못했습니다. ui entrypoint가 root로 default route를 지운 뒤 uid 10001로 내려가 capability를 모두 버리게 했습니다.
- **결과**: `verify-offline.sh` 47개 항목 모두 PASS(medgemma:4b 번들, CPU 생성 약 26초). 이전 설정으로 되돌리면 ui의 route·egress 7개 항목이 FAIL(음성 대조).
- **교훈**: "외부 접속이 안 된다"는 주장은 모든 컨테이너에서 실제로 접속을 시도해 봐야 확인됩니다. 음성 대조로 검사기가 실패를 잡는지도 확인합니다.

## 6. 공개 코퍼스로 현실 확인 (2026-10-07)

- **문제**: toy의 100%는 질문을 문서를 보며 쓴 쉬운 코퍼스의 값이었습니다.
- **시도**: 공개 규제 문서·CC BY 논문·DICOM 표준 발췌 11종(2,029 chunk, 한·영 혼합)과 99문항(한국어 66%, 근거 문장 위치를 테스트로 검증)을 만들었습니다.
- **결과**: 벡터 단독 hit@5 94.9%, 섹션 hit 86.1%, Citation 88.1%(재실행 85.1%), 거절 100%, **오거절 15.2%**, 전체 p50 7.0초. 하이브리드는 더 나빴습니다(hit@5 92.4%, 오거절 25.3%, 검색 p50 4배). 새 실패 3종을 이슈로 남겼습니다: ICH E6(R3)/(R2) 판 혼동([005](issues/005-ich-version-confusion-cross-language.md), #6), DICOM 표 행 chunk 허브([006](issues/006-table-chunks-hubs-and-misses.md), #7), 인용한 부분 답변의 거절 처리([007](issues/007-hedged-answers-counted-as-refusals.md), #8).
- **교훈**: 평가셋은 문서가 다양하고, 같은 내용의 여러 판·번역이 섞인 쪽에서 실패가 드러납니다. 쉬운 코퍼스의 수치는 README 첫 줄에 두지 않습니다.

## 7. B6: 진단·치료 요청 판별 (2026-10-07)

- **문제**: MVP-1 정규식은 "결절/병변/종양"만 들어가도 거절해, 공개 평가셋의 답이 있는 질문 5개를 막았습니다.
- **시도**: 요청 표현만 잡는 정밀 정규식 + bge-m3 kNN(예시 80개, margin은 예시만으로 leave-one-out 조정)으로 바꾸고, 예시와 겹치지 않는 held-out 61문항으로만 평가했습니다.
- **결과**: held-out Precision 95.8%, Recall 92.0%, 오거절 2.8%(MVP-1 정규식: 60.0% / 24.0% / 11.1%). 공개 평가셋의 진단 요청 9개 모두 거절, 답이 있는 질문은 하나도 거절하지 않았습니다.
- **교훈**: 임계값은 held-out을 보기 전에 정하고, held-out에서 찾은 오류(놓친 "맞아도 될까요")는 그 수치에 맞춰 고치지 않습니다.

## 8. 부분 답변 정책 (#8, 2026-10-07)

- **문제**: public 벡터 단독의 오거절 12문항(15.2%)은 모두 MODEL_REFUSED였고, 그중 여러 건은 모델이 정답을 인용해 써 놓고 앞에 "확인할 수 없습니다"를 붙인 뒤 `insufficient_evidence=true`를 돌려준 경우였습니다(교차 문서 오거절 57.1%, [이슈 007](issues/007-hedged-answers-counted-as-refusals.md)). 평가도 이를 거절과 구분하지 못했습니다.
- **시도**: 제품 동작을 바꿨습니다. `insufficient_evidence=true`라도 유효한 context를 인용했고 거절 문장만이 아니면 `partial=true`와 caveat를 붙여 답변으로 돌려줍니다(`PARTIAL_ANSWERS=false`로 이전 동작). 평가는 부분 답변을 따로 세고, 같은 실행을 MVP-1 정책으로도 채점합니다(`legacy_*`).
- **결과** (gemma4:e4b, 벡터 단독, 2회): 오거절 15.2% / 17.7%(MVP-1 정책으로 채점) → **7.6% / 8.9%**. 교차 문서 오거절 57.1% → 14.3%. 대가로 거절 대상 p41 하나가 부분 답변으로 나가 거절 정확도가 100% → **95.0%** 가 됐습니다. p41의 원문은 수치를 `OOmm`로 비워 둔 작성예시이고, 모델은 "수치는 확인할 수 없다"고 정확히 말했지만 평가에서는 실패로 셉니다([이슈 008](issues/008-partial-answer-on-must-refuse.md)).
- **교훈**: 거절과 부분 답변은 다른 사건입니다. 지표가 둘을 섞으면 "보수적인 모델"과 "근거가 없는 질문"을 구분할 수 없습니다. 정책을 바꿀 때는 이전 정책으로 같은 실행을 다시 채점해 차이만 비교합니다.

## 9. B7: cross-encoder reranker (2026-10-07)

- **문제**: 표 행 chunk 허브와 작은 표 미검색(#7), ICH 판 혼동(#6), 그리고 cosine 게이트가 "같은 주제, 답 없음"을 거르지 못하는 문제를 cross-encoder로 줄일 수 있는지 확인해야 했습니다.
- **시도**: `BAAI/bge-reranker-v2-m3`(revision `953dc6f6…`, 2.27GB, Apache-2.0)를 HF 캐시에 한 번 받고, cosine top-30 → rerank → top-5 단계를 선택 기능으로 넣었습니다(torch·transformers는 `rerank` extra, Apple MPS). rerank 점수 게이트는 게이트를 끈 실행 한 번에서 임계값별 결과를 재계산해, 점수를 보기 전에 정한 dev 분할(toy 25 + public 짝수 번째 52)에서만 골랐습니다.
- **결과** (public, gemma4:e4b, 2회씩): 오거절 7.6~8.9% → **5.1%**, Keyword 91.8~93.1% → 94.7~96.0%, 섹션 hit 87.3% → 88.6%, Citation 86.3~87.5% → 88.0%. 파일 hit@5는 96.2% → 94.9%. 답이 있는 질문의 top-5에 들어오던 DICOM 표 chunk 4개가 0개가 됐고 p59(RECIL Table 1)가 풀렸지만, p65(RANO Table 3)는 그대로였습니다. **ICH R3 문항은 더 나빠졌습니다**(R3 hit 5 → 3/7). 검색 p50은 0.11초 → 2.7초(Ollama와 GPU 공유)로 늘었습니다. 게이트는 사전에 정한 목적함수가 0(게이트 없음)을 골랐습니다. dev의 거절 대상은 이미 모두 거절되고 있었기 때문입니다. dev만 보고 만든 두 번째 목적함수는 0.56을 골랐고 held-out 오거절을 7.9% → 15.8%로 두 배로 만들어 채택하지 않았습니다([ADR 0004](decisions/0004-reranker.md)).
- **교훈**: reranker는 "질문과 같은 언어·같은 주제"를 더 잘 고를 뿐, 문서의 판처럼 chunk에 없는 정보는 만들어 내지 못합니다. 게이트 같은 임계값은 dev가 포화되면 튜닝할 근거가 없습니다. 그때 목적함수를 바꾸고 싶어지지만, held-out을 본 뒤에는 바꾸지 않습니다.

## 10. 재현성 확인: 같은 코퍼스, 다른 top-5 (2026-10-07)

- **문제**: B7을 위해 새 DB에 public을 다시 색인하자, 벡터 단독 hit@5가 첫 기준선의 94.9%가 아니라 96.2%였습니다. p68(이슈 006의 "DICOM 표 허브" 대표 사례)이 정답 문서를 찾았습니다.
- **시도**: 두 번째 일회용 DB에 같은 코퍼스를 한 번 더 색인해 embedding과 exact 검색 결과를 비교했습니다.
- **결과**: 오늘 만든 두 색인은 2,029 chunk embedding이 비트 단위로 같았고, 99문항의 exact·HNSW top-5도 같았습니다. 첫 기준선과는 3문항(p68, p95, p98)이 다릅니다. 첫 기준선 DB는 지워서 원인을 확정하지 못했습니다(HNSW 근사 검색 + 코퍼스 사후 필터 가설, [이슈 009](issues/009-retrieval-differs-across-reindex.md)).
- **교훈**: 비교는 같은 색인을 쓴 실행끼리 합니다. 이번 B7·생성 모델 비교는 모두 한 색인에서 실행했습니다. 평가 결과에 DB 상태(코퍼스별 chunk 수, HNSW 파라미터)도 남겨야 합니다.

## 11. 생성 모델 선택 (2026-10-07)

- **문제**: gemma4:e4b는 실행 크기가 10.7GB라 지난 오프라인 번들 검증(Docker VM 7.7GB)에 올리지 못했고, medgemma:4b(4.5GB)로 대신 검증했습니다. 의료 특화 소형 모델로 바꿀지 결정해야 했습니다.
- **시도**: 호스트 Ollama에 이미 있던 두 모델만, 같은 99문항·같은 색인·두 검색 설정(벡터, 벡터 + rerank)에서 2회씩 실행했습니다. 라이선스는 1차 출처(Google 블로그·약관 페이지, HF 모델 카드, `ollama show`)에서 확인했습니다.
- **결과**: medgemma:4b는 메모리가 6GB 이상 작고 생성 p50이 약 1.2초 빨랐지만, 거절 정확도가 75~85%(gemma4 95%)였고 문서에 없는 값을 지어냈습니다(p52 "ICC 0.86", p95 "BICR 최소 30명", [이슈 010](issues/010-medgemma-fabricates-no-answer-values.md)). 영어 질문의 약 74%에 영어로 답했고, 본문 `[n]` 인용은 답변의 약 20%에만 있었습니다. Citation accuracy도 78~85%로 gemma4(86~88%)보다 낮았습니다. 라이선스는 Gemma 4가 Apache 2.0, MedGemma가 HAI-DEF 약관(재배포 시 사용 제한 조항 강제, 약관 사본·NOTICE 제공, 의료기기 제조자 간주 금지)입니다. gemma4:e4b를 유지했습니다([ADR 0005](decisions/0005-generator-model.md)).
- **교훈**: 낮은 오거절률이 좋은 모델을 뜻하지 않습니다. 거절 대상 문항과 함께 보지 않으면 "모든 질문에 답하는 모델"이 가장 좋아 보입니다. "의료 특화"라는 이름보다 근거 밖으로 나가지 않는지가 이 시스템에는 더 중요합니다.

## 12. medgemma는 왜 약했나 (2026-10-07)

- **문제**: "의료 특화 모델"이 의료 문서 RAG에서 더 약한 이유가 지식인지, 프롬프트인지, 근거 사용 방식인지 구분해야 했습니다.
- **시도**: 기존 결과를 문항별로 비교하고, 각 문항의 top-5 chunk 원문(exact 검색으로 원래 결과를 재현)과 답변 속 숫자를 대조했습니다. 그다음 Gemma 3 형식 프롬프트 변형(`--prompt-variant inline-en`, 평가 전용)과 검색 없는 자작 의학 지식 22문항, CT 1장(pydicom 번들 파일)으로 probe했습니다.
- **결과**: 지어낸 값 7건은 모두 정답 근거가 context에 없을 때 나왔고, 4건은 context 속 다른 맥락의 숫자를 붙인 것이었습니다. 근거가 있는데 사전 지식으로 덮어쓴 사례는 없었습니다. 프롬프트 변형으로 거절 정확도 80~85% → 90%, `[n]` 표기 15/82 → 51/79가 됐지만 keyword·citation accuracy는 그대로였습니다. closed-book 문항도 gemma4:e4b가 더 많이 맞혔습니다(두 순서 모두 정답 17 vs 11, 검정력 낮음) ([분석](analysis/medgemma-vs-gemma4.md)).
- **교훈**: 모델 이름의 "의료"는 학습 분포를 말할 뿐, 근거가 없을 때 멈추는 능력을 말하지 않습니다. 비교 상대도 크기·세대가 맞는지 먼저 봐야 합니다(4.3B Gemma 3 vs 8B Gemma 4).

## 13. 실제 프로토콜로 현실 확인 (2026-10-09)

- **문제**: toy(가상 문서)와 public(가이드라인·논문)은 "조항을 묻는" 문서입니다. 이 시스템의 실제 대상인 **임상시험 프로토콜·SAP**(100~240쪽, 개정 이력 표, 가로로 회전된 일정표, 시험마다 같은 섹션 이름)에서 어떻게 되는지 측정한 적이 없었습니다.
- **시도**: ClinicalTrials.gov에 공개된 14개 시험의 프로토콜·SAP 26개와 RECIST 1.1·QIBA 프로파일 2종·프로토콜 2건, 모두 31개 PDF를 **로컬 전용 코퍼스**로 넣었습니다(`classification: licensed-local-only`, 외부 LLM 차단). 원문을 읽고 79문항(한국어 62%, 영상 일정·BICR 절차·반응 기준 적용·영상 관련 선정 기준·SAP 평가변수/중도절단·시험 간 비교·프로토콜↔SAP·같은 주제 무응답·진단 요청·범위 밖)을 썼고, 근거 문장 위치는 로컬 경로에서 테스트로 검증합니다. 질문·근거·답변은 저장소 밖에 두고 **집계 지표만** 커밋했습니다.
  - 추출부터 고쳐야 했습니다. 개정 이력 표의 섹션 번호 인용("5.2 Exclusion Criteria | 변경 내용…")이 헤딩으로 잡혀, DESTINY-Breast06 프로토콜 본문 대부분이 "Appendix G > …" 아래로 들어갔습니다. 번호 헤딩은 **일관된 번호 사슬**(8.1 → 8.1.1 → 8.1.2 → 8.2 …)에 놓일 때만 인정하고, 번호가 부모를 정하게 했습니다(한국어 문서는 "4. → 가. → 1." 구조라 제외, public chunk 수 2,029 그대로). 표 캡션("Table 4 Schedule of Assessments …")은 헤딩으로 잡았습니다. 한 SAP는 텍스트에 NUL 바이트가 있어 인덱싱이 `DB_ERROR`로 실패했고, 추출 단계에서 지웠습니다.
- **결과** (gemma4:e4b, bge-m3 벡터, 한 색인): 8,447 chunk, 인덱싱 약 12분 30초. hit@5 **75.0%**(검색 단계만 보면 79.7%), 섹션/페이지 hit **45.3%**, Citation accuracy **50.0%**, Keyword 63.1%, 거절 정확도 93.3%(exact 실행 86.7%), **오거절 34.4%**, 전체 p50 21.6초. public(96.2% / 87.3% / 86~88% / 7.6~8.9% 오거절)보다 모든 지표가 크게 낮습니다. 실패는 세 가지였습니다.
  1. **시험 식별자가 없는 chunk**([이슈 012](issues/012-chunks-without-trial-identity.md)): top-5 chunk의 48.8%가 질문한 시험이 아닌 다른 시험 문서였습니다. 스폰서 문서는 시험 약칭을 거의 쓰지 않고(ELARA 0줄, ECHELON-1 0줄), "1.1 Synopsis"·"8.1.1 Tumor Imaging"은 모든 프로토콜에 있습니다. 모델은 다른 시험의 근거로 질문한 시험의 답처럼 답했습니다.
  2. **B6 분류기의 오거절**([이슈 011](issues/011-scope-classifier-refuses-protocol-imaging-questions.md)): "MRI를 언제 찍는가", "PET 결과에 따른 치료 분기" 같은 7문항(답 있는 질문의 10.9%)을 진단 요청으로 막았습니다. public에서는 0건이었습니다.
  3. **PDF 기호 손실**([이슈 013](issues/013-pdf-glyph-loss-and-rotated-tables.md)): RECIST 원문의 `≥`가 `P`로, "6–8 weeks"가 "68 weeks"로 추출되고, 모델은 "P15 mm 이상"을 그대로 옮겼습니다(키워드 채점은 정답으로 셈). 가로 회전된 일정표는 pypdf로 행·열을 복원하지 못해, 일정표를 행 단위로 펼치는 처리는 하지 못했습니다.
  - [이슈 009](issues/009-retrieval-differs-across-reindex.md)(#10)의 원인도 확인했습니다. HNSW를 쓸지는 플래너가 정하는데, 혼합 DB에서는 코퍼스 필터 때문에 exact(seq scan)를 고르고, public만 든 DB에서는 HNSW를 골라 근사 결과가 그래프(삽입 순서)에 따라 달라집니다. public-only 복사본에서 HNSW top-5는 exact와 4문항 달랐고 hit@5가 첫 기준선과 같은 94.9%였습니다. `ef_search=200`이면 0문항입니다. 이번 private 실행은 HNSW와 exact의 top-5가 79문항 모두 같았습니다.
  - 검색 단계만 비교하면 B7 reranker(exact top-30 → top-5)가 파일 hit@5 79.7% → 85.9%, 섹션/페이지 hit 45.3% → 71.9%로 public(섹션 hit +1.3%p)보다 훨씬 큰 이득을 냈습니다. 질문 속 시험 이름·조건을 cross-encoder가 읽기 때문으로 보이지만, 생성까지 포함한 평가는 호스트 수면으로 끝내지 못했습니다.
- **교훈**: 쉬운 코퍼스에서 맞춘 단계(OUT_OF_SCOPE 예시, 섹션 경로만 담은 chunk 머리말)는 실제 문서의 다른 분포에서 깨집니다. 여러 문서가 같은 구조를 공유하면 "어느 문서인가"가 chunk에 들어가야 하고, 이것은 reranker나 생성 모델이 대신할 수 없습니다. 실패를 본 뒤의 수정은 이 평가셋으로 재지 않고 새 held-out으로 잽니다.

## 14. EmbeddingGemma 2를 bge-m3와 다시 비교 (2026-10-10)

- **문제**: 호스트 Ollama를 0.24.0 → 0.40.2로 올렸고, 호스트에 `embeddinggemma-2:270m`·`:740m`이 있었습니다. 한국어 성능은 공개되지 않았고 bge-m3와 직접 비교한 수치도 없었습니다. 지금까지의 수치는 0.24.0 결과라 **0.40.2에서 bge-m3 기준선부터 다시** 재야 했습니다.
- **시도**: 모델마다 일회용 DB에 toy·public·private를 새로 색인하고(chunk 32 / 2,029 / 8,447), exact 검색·gemma4:e4b로 toy 1회, public 2회, private 1회와 `make scope-eval`을 돌렸습니다. 임계값 2개(`scope_margin`, `min_relevance_score`)는 모델마다 예시 또는 dev만으로 다시 정했고, 목적함수는 측정 전에 보고서에 적었습니다. 설정은 bge-m3, 270m 768d / 512d / 256d입니다.
  - **먼저 부딪힌 것**: Ollama 0.40.2가 gemma4:e4b에서 thinking을 기본으로 켜서 짧은 질문에도 660토큰, 질문당 약 45초가 걸렸습니다(0.24.0 때 p50 4.4초). `think:false`를 보내도록 하고, thinking으로 돌린 첫 기준선은 버렸습니다. 같은 이유로 **생성 지표는 0.24.0과 직접 비교하지 않습니다.** 반면 bge-m3 벡터는 표본 20개에서 cosine 최소 0.99998로 사실상 같았고, 검색 지표는 0.24.0과 같았습니다.
  - Ollama 0.40.2 `/api/embed`는 `dimensions`를 지원하고, 결과가 "앞 N차원 절단 + L2 정규화"와 같아서(오차 6.6e-8) 그대로 `EMBEDDING_TRUNCATE_DIM`으로 보냅니다.
  - **270m과 740m의 텍스트 벡터는 비트 단위로 같았습니다.** `ollama show` capability(740m: embedding·vision·audio, 270m: embedding)와 합쳐 740m은 vision·audio 타워를 더한 모델로 보이지만(추정, 가중치는 직접 비교하지 않음) 텍스트 벡터가 같아 740m 측정은 생략했습니다.
- **결과**: 270m은 같은 색인·같은 규칙에서 bge-m3보다 검색이 낮았습니다. public hit@5 96.2% → 92.4%, 섹션 hit 87.3% → 81.0%, toy hit@5 100% → 89.5%, private 섹션 hit 45.3% → 34.4%. 512d는 768d와 public hit@5·섹션 hit에서 거의 같았고, 섹션 hit는 256d가 모든 코퍼스에서 가장 낮았으며(public 79.7%, private 31.2%) hit@5 차이는 public 1문항(72 대 73·79 중), private 4문항(44~48/64: 768d 68.8%, 256d 70.3%, 512d 75.0%)이었습니다. B6 판별기의 오거절은 2.8% → 5.6~8.3%로 늘었습니다. 270m의 이득은 크기(디스크 약 1/3, 적재 `ollama ps` 346MB 대 673MB로 약 1/2)와 질문 embedding p50 3.6ms 차이(13.3ms 대 16.9ms)뿐입니다. 상세: [ADR 0002](decisions/0002-embedding-model.md) "2026-10 재평가". **bge-m3 유지를 권고**하고 기본값은 바꾸지 않았습니다.
  - 사전 등록한 cosine 게이트 목적함수(dev의 `거절 정확도 − 오거절률`)는 모든 모델에서 "게이트 없음"을 골랐습니다. dev의 거절 대상은 범위 판별기·생성 모델이 이미 거의 다 거절해서 게이트가 얻을 것이 없었기 때문입니다. B7 reranker 게이트에서 본 포화(§9)와 같은 현상이고, 규칙을 바꿔 다시 맞추지 않았습니다.
- **교훈**: 런타임을 올리면 모델 비교 전에 **기준선을 다시** 재야 합니다. 이번에는 임베딩은 그대로였는데 생성 동작(thinking)이 바뀌어 속도가 10배 느려졌습니다. 또 같은 이름의 변종(270m / 740m)이 같은 텍스트 벡터를 낼 수 있어, 측정 전에 출력이 다른지부터 확인하면 시간을 아낍니다.
- **측정 안 함**: 문서별 실제 제목을 넣은 문서 접두어(`title: none`만 측정), 128차원, 740m의 멀티모달, Ollama 270m 빌드(nvfp4)의 양자화 영향, private의 모델당 2회 이상 실행.

## 15. 업무 문서를 변환 없이 바로 넣기 (2026-10-11)

- **문제**: 실제 업무 문서 87건(로컬 전용, 내용·파일명 비공개)을 넣어 보니 그대로 색인되는 것은 **21건**뿐이었습니다. docx 25·xlsx 35·doc 1은 미지원이었고, 서명본 PDF 5건은 권한 암호만 걸린 AES PDF라 `ENCRYPTED_PDF`로 빠졌습니다. 그때는 저장소 밖 변환 스크립트(docx·xlsx → Markdown, PDF 복호화)로 우회했습니다.
- **시도**: docx·xlsx 추출기를 표준 라이브러리만으로 만들고(#17), `cryptography`를 기본 의존성으로 넣어 권한 암호만 있는 PDF를 열었습니다. 개발은 합성 문서(`samples/office/`)로만 했고, 업무 문서는 머지 뒤 로컬에서 숫자만 냈습니다.
  - 리뷰가 다섯 번 돌았습니다. 기능은 첫 회에 통과했지만, 일부러 만든 작은 파일 하나가 메모리를 GB 단위로(한 건은 CPU를 수십 초) 쓰게 하는 경로가 회차마다 나왔습니다(같은 데이터를 가리키는 시트 반복, 먼 열 하나, 공유 문자열 × 셀 수, 머리글 × 행 수, 셀 안 중첩 문단, 극단적 압축률 등 9개). 텍스트 예산(해제 바이트의 2배)·압축률·깊이·폭 상한으로 막고, 남은 2개는 이슈로 분리했습니다(#18, #19). 실무 문서 60건의 압축률은 최대 65배로 상한(100배)에 걸리지 않았습니다.
  - 재측정에서 버그를 하나 더 찾았습니다. 변환본과 비교한 단어 일치율이 일부 docx만 61~86%였고, XML 구조로 따라가 보니 **행이 하나뿐인 표**(상자로 두른 주의 문구, 제목 블록)의 텍스트가 사라지고 있었습니다. 그 행이 머리글이 된 뒤 짝지을 본문 행이 없었기 때문입니다. 행 1개 표 27개 중 21개가 해당했고, 고친 뒤(#20) 단어 종류 기준 일치율이 최저 67.8% → 98.4%가 됐습니다.
- **결과** (bge-m3, exact, reranker 없음, Ollama 0.40.2, 집계: `eval/results/2026-10-11_local-work-docs_*`):
  - 바로 색인: 87건 중 **21 → 86건**(남은 1건은 `.doc`, "docx로 저장 후 다시 넣으세요" 안내). chunk는 1,776 → 16,950개로, 대부분 xlsx 행입니다.
  - 최신판 16건만 넣고 42문항에서 정답 파일이 top-5에 드는지: **원본 그대로 39/42**, 예전 변환본 37/42(같은 코드·같은 조건). 둘 다 맞힌 것 36, 원본만 3, 변환본만 1입니다. 변환 스크립트 없이도 검색이 같거나 낫습니다.
- **교훈**: "다른 형식을 읽는다"는 기능보다 **읽은 결과가 예전 경로와 같은지**를 숫자로 확인하는 단계가 버그를 찾았습니다. 합성 문서 테스트는 모두 통과했지만, 실제 문서에 흔한 한 줄짜리 표는 합성 문서에 없었습니다.
- **측정 안 함**: 답변 정답률(채점하려면 답변을 읽어야 해서 이번에는 하지 않음), reranker를 켠 검색, 모든 판본을 넣은 코퍼스의 검색. xlsx 행이 다른 문서를 밀어내는 문제는 판본 필터·스코프 작업(3b·3c)에서 다시 봅니다.

## 16. 문서 판(edition) 메타데이터와 최신판 기본 검색 (2026-10-11)

- **문제**: 같은 문서의 여러 판이 한 코퍼스에 있으면 옛 판이 검색되고 옛 판의 내용이 사실처럼 답으로 나갑니다(이슈 005: ICH E6(R3) 질문 7개 중 6개의 top-5를 E6(R2) 안내서가 채움). 문서 행에 판 정보가 없었습니다.
- **시도**: [ADR 0006](decisions/0006-document-versions.md). 판은 `.corpus.yaml`의 `versions:`(명시) 또는 파일명 토큰(추정)에서 읽고, 같은 (corpus, family) 안에서 번호를 숫자로(날짜는 manifest에 적은 것끼리만) 비교해 최신판을 정합니다. 비교할 수 없거나 같으면 둘 다 최신으로 둡니다. 검색은 기본이 최신판만이고(`is_latest`, 벡터·하이브리드 두 채널), 요청의 `includeSuperseded`·설정 `SEARCH_LATEST_ONLY`·UI "옛 판 포함"으로 켤 수 있습니다. 인용에는 판이 붙고, 옛 판이 인용되면 경고가 붙습니다. chunk·embedding은 그대로라 재색인이 필요 없습니다(Alembic 0007은 기본값으로 채움).
- **결과** (공개 코퍼스 99문항, bge-m3, exact, gemma4:e4b, Ollama 0.40.2, 같은 색인(2,029 chunk)에서 `SEARCH_LATEST_ONLY=false` 2회 대 `true` 2회. `eval/results/2026-10-11_public_*latest{off,on}*`):

| | 끔 (1회 / 2회) | 켬 (1회 / 2회) |
|---|---|---|
| hit@5 / 섹션 hit | 96.2% / 87.3% (같음) | 94.9% / 84.8% (같음) |
| Citation 정확도 | 86.7 / 85.3% | 90.7 / 90.7% |
| Keyword coverage, 거절 정확도 | 92.0%, 95.0% | 92.0%, 95.0% |

  - ICH E6(R3) 7문항(p10~p16)의 top-5에서 R2 chunk(05번 문서)가 **27개 → 0개**, R3(02번)가 8개 → 29개(나머지 6개는 다른 문서)가 됐습니다(두 번 모두 같음). 이 7문항 가운데 파일 hit 5 → 7, 인용 정확 2 → 7입니다. p10은 여전히 섹션 hit가 아닙니다(R3 chunk는 잡히지만 2.5 절이 아님).
  - **이 7문항은 실패를 본 뒤 고친 것이라 위 개선은 "실패 재확인"일 뿐 새 held-out 증거가 아닙니다.**
  - **잃은 것**: p32·p33·p34의 정답 파일이 05번(R2 안내서)으로 적혀 있어 hit·섹션 hit·인용이 모두 miss가 됐습니다(hit@5 −3문항, +2문항은 p10·p12). 세 문항 모두 답은 R3 chunk로 나왔고 거절되지 않았으며 Keyword coverage는 변하지 않았습니다(답 내용의 정확성은 읽어서 채점하지 않음). p33·p34는 문서를 지목하지 않은 질문이라 이 감소의 상당 부분은 "정답 파일이 옛 판"이라는 평가셋의 정의 때문입니다. 반면 p32는 "ICH GCP 안내서에 따르면"처럼 옛 판 문서를 이름으로 요청한 질문인데 최신판 기본값이 그 요청까지 막은 것이라 평가셋이 아니라 기능의 한계입니다("옛 판 포함"을 켜거나 질문 속 판·문서 이름으로 거르기가 필요). 평가셋은 바꾸지 않았습니다.
- **교훈**: 옛 판을 숨기면 "정답 파일"의 정의가 판에 의존한다는 점이 드러납니다. 판이 있는 코퍼스의 평가셋은 정답을 판 단위로 적어야 비교가 공정합니다(이번에는 고치지 않음).
- **업무 문서에서** (로컬 전용 87건, 정답 파일 top-5 42문항, bge-m3, exact, 같은 색인에서 판정만 바꿔 검색, 집계: `eval/results/2026-10-11_local-work-docs_versions_*`). 기준은 사람이 고른 최신판 16건 목록입니다.
  - 처음 쟀을 때 파일명 추정이 **최신판 2건을 숨겼습니다**. 파일명에 판이 둘 있는 문서(`… v2.1 v2.2`, 판에서 판으로의 변경을 담은 문서)를 앞 판만 읽어 서로 다른 변경 문서를 한 문서의 판처럼 비교했기 때문입니다. 판 토큰이 둘이면 단독 문서로 두게 고친 뒤 0건입니다.
  - 추정은 안전했지만 효과가 작았습니다. 옛 판 71건 중 9건만 숨겼고, 나머지는 새 판과 이름이 판 말고도 달라(접미어·폴더) 묶이지 못했거나 판 번호가 같았습니다. 그래서 추정으로 `.versions.yaml` 초안을 만들고 운영자가 확인하는 도구(`scripts/draft_versions.py`)를 붙였습니다.

| 판정 | 숨긴 옛 판 / 71 | 숨긴 최신판 / 16 | 정답 파일 top-5 | top-5 중 옛 판 chunk |
|---|---|---|---|---|
| 필터 끔 | – | – | 21 / 42 | 79.5% |
| 파일명 추정만 | 9 | 0 | 24 / 42 | 75.2% |
| 초안 그대로 (날짜는 주석) | 13 | 0 | 26 / 42 | 74.3% |
| 초안 + 날짜 후보 모두 확정 | 24 | 0 | 26 / 42 | 73.8% |
| 운영자 확인 결과 (최신판 목록) | 71 | 0 | **39 / 42** | 0% |

  - 초안은 어떤 단계에서도 최신판을 숨기지 않았지만, 확인 결과에 이르려면 초안 판정 87건 중 **58건**을 운영자가 바꿔야 했습니다(날짜를 모두 확정해도 47건). 이 문서들에서 "어느 것이 최신판인가"는 파일명에 거의 들어 있지 않고 사람이 아는 정보였습니다. 운영자에게는 87건을 하나씩 고치는 것보다 **최신판 16건을 고르는 것**이 훨씬 적은 일이므로, 다음 개선은 최신판 목록을 직접 지정하는 형식입니다(측정 안 함).
  - 최신판 목록을 지정하면 정답 파일 top-5가 39/42로, 최신판 16건만 넣은 코퍼스(§15)와 같아집니다. 판 관리의 효과는 크지만 그 효과의 대부분은 사람이 준 정보에서 나옵니다.
- **측정 안 함**: 옛 판 포함 검색의 답변 품질, 질문 속 판 이름 필터, chunk 머리말의 판 정보, 최신판 목록 지정 형식.

- 사람 또는 LLM 채점에 의한 답변 품질. 지금은 키워드·인용 위치 지표뿐입니다.
- 새 held-out 셋으로 검증한 rerank 점수 게이트, chunk에 문서 판·시험 식별자를 넣은 뒤의 #6·#13 재측정.
- 실제 프로토콜 코퍼스에서 기본 설정 2회차와 reranker를 켠 생성 평가(호스트가 배터리 절전 수면에 들어가 중단, 아래 README 참고). 회전된 일정표의 행 복원.
